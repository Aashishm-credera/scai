## 1. What this is

The head app for the abc sites. It is built with **Next.js** (App Router) and **TypeScript**, and
the content lives in **SitecoreAI**. One app serves several sites (multisite) in English and
Spanish.

**We do not build pages, we build components.** Authors assemble pages from our renderings in
Page Builder. Each rendering has to work whatever an author does with it, including leaving it
empty.

You will deal with three things constantly:

- **Renderings.** Components an author can place, under `src/components/`.
- **The design system.** The UI itself, under `src/design-system/`, built and reviewed in
  Storybook without Sitecore.
- **Design tokens.** Every colour, size and spacing value, generated from one Figma export.

---

## 2. How a page is made

```
Someone visits /es/heart-health
        ↓
src/proxy.ts                     preview, bot tracking, locale, site, redirects, personalize
        ↓
src/app/[site]/[locale]/[[...path]]/page.tsx
        ↓
src/lib/cache/get-sitecore-page  fetches the layout from Experience Edge, cached with sc: tags
        ↓
Sitecore returns a layout:       "a Container holding a HeadingText and a BaseButton"
        ↓
.sitecore/component-map.ts       turns each name into one of our renderings
        ↓
Our renderings render            content arrives as `fields`, author settings as `params`
```

**Sitecore sends names, and the component map turns them into components.** A name missing from
the map shows a "component not found" placeholder. The map is generated, so you never edit it by
hand.

## 3. Where everything lives

```
src/
  app/                    Next.js routes and API route handlers. Rarely touched.
  design-system/          FE. The UI, with no knowledge of Sitecore.
    design/                 tokens, icons and logos pages
    ui/                     generated shadcn base UI
    atoms/                  one element each, Base-prefixed folders
    molecules/ organisms/
    tokens/generated/       GENERATED CSS
  components/             Sitecore renderings. Every .tsx here is scanned into the map.
    foundation/             shared field helpers, .ts only
    features/<Group>/       one rendering per folder
    Project/<site>/         site-specific renderings
    sxa/                    SXA out-of-the-box renderings
    content-sdk/            SDK plumbing, kept out of the map
  lib/                    Sitecore client, cache helpers, metadata, component-props helpers
  i18n/                   Languages and next-intl setup
  proxy.ts                Request pipeline

design-tokens/            Token pipeline: figma-export.json in, generated/ and reports/ out
.storybook/               Storybook setup
.sitecore/                GENERATED by the Sitecore CLI
../../authoring/          Serialized Sitecore items: templates, renderings, styles, variants
```

Files marked GENERATED are rebuilt by a command and committed. A hand edit disappears on the
next build, and CI fails because the committed file no longer matches what the build produces.

## 4. The rules for renderings

**1. The filename is the rendering name.**
`features/PageContent/HeadingText/HeadingText.tsx` registers as `HeadingText`, and must match
the rendering item in Sitecore exactly. Two files with the same name anywhere under
`src/components/` collide, and one silently wins.

**2. No `index.ts` under `src/components/`.**
It would register a rendering called `index`. Barrels are fine in `src/design-system/`.

**3. A rendering adapts a design-system component.**
The markup lives in `src/design-system/`. The rendering reads Sitecore data and passes it on, and
the design system never imports from `src/components/`:

```tsx
// src/components/features/Navigation/BaseButton/BaseButton.tsx
import { Button } from '@/design-system/atoms/BaseButton';

export const Default = ({ fields, params, page }: BaseButtonProps) => (
  <Button
    variant="primary"
    linkField={getFieldValue(getDatasource(fields)?.Link)}
    styles={params.styles ?? ''}
  />
);
```

Each named export (`Default`, `Secondary`, …) is a variant that matches a Headless Variant in
Sitecore. Props live in a sidecar, `base-button.props.ts`, which the map ignores.

**4. Pass `params.RenderingIdentifier` and `params.styles` through.**
Without them, the style an author picks and any anchor link to the component silently do
nothing on the live site. It looks fine locally, which is what makes it dangerous.

**5. Treat every field as possibly missing.**
Authors add a component before filling it in, and unpublished content arrives as `undefined`.
With no datasource, render nothing on the published page and a hint in Page Builder. A crash here
takes down the whole page.

Start a new rendering with the scaffold, which writes the component and its props sidecar:

```bash
npx sitecore-tools project component scaffold features/<Group>/<Name>/<Name>
npm run sitecore-tools:generate-map
```

Helix layering applies: `Project` may use `features`, `features` may use `foundation`, and a
feature never imports another feature.

## 5. Colours, sizes and spacing

Nothing is hard-coded. Every value comes from the Figma export.

```
design-tokens/figma-export.json                 the designer exports this
        ↓  npm run tokens:build
src/design-system/tokens/generated/primitives.css   raw scales
src/design-system/tokens/generated/semantic.css     named roles, built from the scales
src/design-system/tokens/generated/theme.css        Tailwind and shadcn wiring
design-tokens/generated/tokens.ts                   the same values, for code
```

**Use the token that names a purpose.** `--abc-surface-brand-brand-1` ("the main brand surface")
keeps working when the brand colour changes. `--abc-color-brand-primary-500` ("this red") has to
be hunted down. Raw hex in a component is caught in review.

Breakpoints are **480, 1024 and 1600px**, on Tailwind's `md:`, `lg:` and `xl:`. The stock `sm:`
and `2xl:` are switched off and compile to nothing.

`tokens:breaking` fails when a token disappears. If the removal is intended, review
`design-tokens/reports/changes.md` and run `npm run tokens:baseline`.

### Author styles

Style options authors pick in Sitecore (`button-icon-right`, `description-text-size-l`) arrive
in `params.styles` as plain class names. Give them CSS. Tailwind only ships classes it can see
in source, so a Tailwind utility typed into Sitecore works in development and vanishes in the
production build.

## 6. Storybook

```bash
npm run storybook
```

It is the only way to see a component without SitecoreAI access, and it needs no credentials.
Stories live in each module's `stories/` folder under `src/design-system/`, never under
`src/components/`: a rendering only maps data onto a component, so the component's story shows
what authors get.

Storybook is also where accessibility is checked automatically. `npm run test:storybook` fails
on any axe violation, so a component without a story is a component nothing checks.

---

## 7. Languages

Page text comes from Sitecore and is already translated, because each page is fetched for one
language. Text in our code (button labels, screen-reader text) comes from the Sitecore
dictionary through next-intl.

English and Spanish are enabled in `src/i18n/locales.ts`. Each language must also exist in
Sitecore.

---

## 8. Caching and publishing

Pages render on request and are cached with Next.js Cache Components (`'use cache'`), tagged by
site, route and item. Publishing in Sitecore calls `POST /api/revalidate`, which clears the
matching tags, so published content appears without a redeploy.

Preview and Page Builder go through `src/app/api/editing/` and are never cached. The
`src/app/api/dataweavers/` routes manage the Dataweavers page cache on the hosted environments.

## 9. Running it locally

```bash
npm install
npm run playwright:install    # once per machine, for the accessibility tests
npm run storybook             # design system, no credentials
npm run dev                   # the site, needs .env.local
```

Copy `.env.remote.example` (or `.env.container.example` for local containers) to `.env.local`.
Without credentials the site cannot start, because it cannot fetch the site list. Storybook,
tests and type checks still work: `npm run sitecore-tools:build:offline` generates the
`.sitecore` files without Experience Edge.

### Before you push

```bash
npm run verify
npm run type-check
```

Together these run what the frontend checks pipeline runs.

## 10. Branches, CI and deploys

- PRs target `develop`, one squashed commit per PR. Merges from `develop` to a `release/*` or
  production branch keep a merge commit.
- `.pipelines/abc-sites-frontend-checks.yml` runs lint, formatting, types, tests, tokens, icons
  and Storybook checks, and deploys nothing. It runs on PRs once it is added as build validation
  on `develop`.
- `.pipelines/arc-head-standard-release.yml` deploys this app from `develop` to DEV, TEST or UAT,
  each behind an approval. The Sitecore pipeline is separate and promotes in order
  (DEV → TEST → UAT). A rendering that needs new Sitecore items should not reach an environment
  before its items do.
- The pipelines are owned by Dataweavers. Ask before changing a release pipeline.

## 11. When something breaks

**"Component not found" on a page.**
The name Sitecore sent is not in the map. Check that the filename matches the rendering item,
that it sits under `src/components/`, and rerun `npm run sitecore-tools:generate-map`.

**An author style does nothing.**
`params.styles` is not passed to the root element, or the class has no CSS (see 5).

**Published content does not appear.**
The webhook did not reach `POST /api/revalidate`, or used the wrong secret. See `AGENTS.md`.

**`npm run dev` fails with a configuration error.**
Missing credentials. Use Storybook for component work.

**CI fails on a generated file.**
Something changed upstream without its build being rerun. Run `npm run tokens:build`,
`npm run icons:build` or `npm run sitecore-tools:generate-map`, and commit the result.

**The rendering map has a component called `index`.**
Someone added an `index.ts` under `src/components/`. Delete it.
